Added `ControllerManager::rescanDevices()` (new `requestRescanDevices` signal → `slotRescanDevices` slot, mirroring the existing `requestSetUpDevices` pattern for safely crossing onto the ControllerManager's own thread), exposed as `Q_INVOKABLE rescan()` on `QmlControllerManagerProxy`, with a "Rescan" button added to `Settings/Controller.qml`. - ~~Automatic OS-level hotplug detection~~ — **✅ RESOLVED, IMPLEMENTED and user-verified (2026-08-01).** Plugging/unplugging a controller now updates the Controllers list automatically (no Rescan click), verified with the real Ion Discover DJ across repeated plug/unplug cycles with the QML Controllers page open, no crashes. This was a deep rabbit hole; the final working design and every disproven theory along the way:
  - **`ControllerHotplugMonitor`** (new `src/controllers/controllerhotplugmonitor.h/.cpp`, macOS-only, no-op stubs elsewhere): CoreMIDI `MIDIClientCreate` notification callback + IOKit `IOHIDManager` device-matching/removal callbacks, debounced (300ms, coalesces bursts) into one `devicesMayHaveChanged()` signal. Constructed/started at the END of `slotSetUpDevices()` (NOT `slotInitialize()` — IOHIDManager fires immediately for already-connected devices at registration, which raced the startup device-open loop and caused a real, root-caused segfault). Connected to **`slotSetUpDevices()`, not `slotRescanDevices()`** — every rescan replaces all `Controller` instances with fresh CLOSED ones, so re-running the full setup sequence is what re-opens config-enabled controllers with their mappings afterwards (also the desired UX: plug in an enabled controller → it comes up ready to use).
  - **Critical macOS threading gotcha (cost hours):** Qt does NOT integrate a worker `QThread`'s event loop with its CFRunLoop (only the GUI thread gets the CoreFoundation dispatcher) — so callbacks scheduled on the ControllerManager thread's run loop were NEVER delivered, despite a standalone test tool proving the OS sends them fine. Also, CoreMIDI delivers ALL notifications process-wide to the run loop current at the process's FIRST `MIDIClientCreate` (which is PortMidi's, on the ControllerManager thread). Fix: a 250ms `QTimer` pump in the monitor draining `CFRunLoopRunInMode(kCFRunLoopDefaultMode, 0, true)` on that thread. What looked like "MIDI hotplug working" in earlier testing was actually just startup enumeration.
  - **`IOHIDManagerOpen` + `kIOReturnExclusiveAccess` saga:** match-all (`nullptr`) criteria makes `Open()` fail wholesale with `kIOReturnExclusiveAccess` because WindowServer holds the built-in keyboard/trackpad exclusively. NOT a TCC/Input Monitoring problem — proven by signing a real hardened-runtime bundle with a stable identity (`build-bundle/Deo DJ.app`, Apple Development cert) and observing the app never even *registers* in Input Monitoring settings, plus `log show` showing tccd never receives a request. Fix: allow-list matching set (Generic Desktop Joystick/GamePad/MultiAxis + every vendor-defined usage page 0xFF00–0xFFFF + exact usages of already-connected non-keyboard/mouse/pointer devices) — keyboard/mouse excluded, so no Input Monitoring permission is even needed. Note: the Ion Discover DJ turned out to be a **class-compliant USB-MIDI device, not HID at all** (confirmed via `ioreg`: Audio-class/MIDIStreaming interface, driven by Apple's `MIDIServer`), so the MIDI path is what detects it; the HID path is for genuinely-HID controllers.
  - **PortMidi staleness bug:** the vendored (old SourceForge-era) PortMidi builds its device table ONCE in `Pm_Initialize()`; `Pm_CountDevices()`/`Pm_GetDeviceInfo()` index a static snapshot, so unplugged devices reappeared in every rescan forever. Fix: `PortMidiEnumerator::queryDevices()` now cycles `Pm_Terminate()`/`Pm_Initialize()` on every call (safe: all old controllers are closed first; this PortMidi vintage never disposes its CoreMIDI client, so re-init re-enumerates live state cleanly).
  - **Use-after-free crash on unplug (root-caused via lldb attach + `get-task-allow` entitlement):** `EXC_BAD_ACCESS` in `QmlControllerDeviceProxy::getType()` reading a deleted `Controller*`. Three-layer fix: (1) `ControllerEnumerator::retireDevice()` (base-class) — enumerators now close dropped controllers immediately but defer the `delete` by 15s, covering the queued-signal window in which the main thread still reads old pointers; (2) `QmlControllerManagerProxy::refreshKnownDevices()` was **add-only** — it now prunes proxies whose wrapped controller vanished (also fixes duplicate list entries piling up per rescan, since every rescan creates new `Controller` objects even for still-connected hardware); (3) `QmlControllerDeviceProxy::m_pInternal` is now a `QPointer<Controller>` with null guards in every accessor, so any residual stale read degrades to "N/A" instead of crashing.
  - **Two more pre-existing bugs fixed in passing:** `HidEnumerator::queryDevices()`/`BulkEnumerator::queryDevices()` never cleared `m_devices` between calls — every rescan APPENDED a duplicate controller object for each still-connected device (latent upstream bug, exposed once rescans became routine).
  - **Build/test infrastructure note:** verification used the signed bundle workflow (`build-bundle/`, `MACOS_BUNDLE=ON`, `AU_EFFECTS=OFF` for fast iteration, manual `codesign --options runtime` with the dev entitlements in scratchpad incl. `com.apple.security.get-task-allow` for lldb). The bare `build/` binary workflow still builds clean and is unaffected. The signed bundle turned out NOT to be required for hotplug (the exclusive-access fix was the real unblock), but it remains useful for anything TCC-gated (camera etc.).
  - **⚠️ CORRECTION (2026-08-02): the reason given here for turning `AU_EFFECTS=OFF` was WRONG.** The slow startup was blamed on Hardened Runtime re-verifying every AudioUnit plugin's signature on each launch. It isn't. Rebuilt with `AU_EFFECTS=ON` and signed ad-hoc with Hardened Runtime *disabled*, the first launch was still many minutes. The real cause is simply the size of this machine's plugin collection: **65 AudioUnits** (NeuralNote, Supercharger, Replika, Raum, Guitar Rig 7, the Kilohearts suite, ...), each logging "took more than 2000 ms to initialize" as Mixxx instantiates it to read its manifest. Signing mode is irrelevant. **And critically, the cost is a ONE-TIME cache-warm, not per launch: the second launch took 26 seconds.** macOS caches the AU validation per binary, so it recurs only when the binary or the plugin set changes. `AU_EFFECTS=ON` is therefore perfectly practical for the real app and is what the shipped `dist/` bundle now uses; keep `AU_EFFECTS=OFF` only for the *test* build, where the genuine AudioToolbox deadlock (see M15) still applies. **Also corrected: an 8-hour "hang" observed while measuring this was a monitoring artifact, not a hang** — the watcher was grepping for a log marker that never appears in that configuration; a `sample` of the process showed the main thread idle in the normal Qt event loop, i.e. the app had started fine.
- **⚠️ Major discovery: the QML skin's entire native Settings surface (`res/qml/Settings.qml` + all of `res/qml/Settings/*.qml`, including everything built for M11's Broadcast page and this session's new Controller rescan button) is currently unreachable in the running app.** The only working "⚙ Preferences" button in `main.qml` calls `Mixxx.PreferencesDialog.show()`, which opens the **legacy Qt Widgets dialog** (`DlgPreferences`/`DlgPrefControllers`/etc.), not the QML `Settings.qml` Popup. `Settings.qml` is a fully-built, self-contained component (expects its category pages passed in via a `sections` list) but is never instantiated anywhere in the skin — confirmed via an exhaustive grep, zero instantiation sites. - **Stage 4 (2026-07-28) — RESOLVED: the two-pipeline rewrite, finally done.** User reported a new, structurally distinct bug: dragging a deck's audio to a silent/out-of-bounds position (deck genuinely paused, no audio) left its video still visibly animating. - **Stage 5 (2026-07-28) — RESOLVED: rate-matching (tempo/pitch/sync tracking).** User asked to finish the three remaining M12 items (rate-matching, NDI output, GPU preview) in one pass; sequenced rate-matching first since it touches existing hot sync code (smallest of the three). - **Stage 7 (2026-07-28) — ATTEMPTED, found broken in real-world testing, DISABLED pending further debugging.** User explicitly chose to attempt the full zero-copy GPU path (GStreamer `glupload`/GL-memory buffers → a shared `GstGLContext` wrapping Qt Quick's own native CGL context → raw GL texture ids wrapped into `QSGSimpleTextureNode`s via `QRhiTexture::createFrom()`/`QQuickWindow::createTextureFromRhiTexture()`) despite an explicit upfront warning that this was the one piece of the whole video engine impossible to verify without real, hands-on use — GL-context-sharing/cross-thread-texture-lifetime work this codebase had never done before. - **Camera input (Stage 3y) — ✅ NOW REAL-HARDWARE VERIFIED and a genuine latent bug fixed (2026-08-01).** Previously blocked on the `MACOS_BUNDLE` packaging gap; unblocked by the signed-bundle workflow M8 established. Two independent blockers, both real:
  1. **Missing camera entitlement.** Under Hardened Runtime, `NSCameraUsageDescription` in Info.plist is NOT sufficient — tccd refuses to even *prompt* for `kTCCServiceCamera` without `com.apple.security.device.camera`, and silently denies. It was missing from **both** the dev entitlements and the real shipped `packaging/macos/Mixxx.entitlements`, so this would have broken camera in any release build too. Added to both. Diagnosed from a `log stream --predicate 'process == "tccd"'` capture, which named the missing entitlement outright.
  2. **Launch-context attribution.** Launching the app from a terminal/agent shell makes macOS treat the *parent* process as TCC's "responsible process"; since that parent had no camera entitlement, TCC denied without prompting. Launching detached via `open` makes the app responsible for itself and the prompt appears normally. Not a code bug — but a permanent gotcha for any TCC-gated feature tested this way.

- **GPU-upload preview path (Stage 7) — second attempt 2026-08-01: THREE real bugs found and fixed, but a fourth blocker remains; path is DISABLED again.** The fixes below are all committed and correct, and materially de-risk a future attempt — the remaining blocker is narrow and now precisely located:
  1. ~~"GstGLMemory/QRhiTexture lifetime"~~ (the original hypothesis) — **wrong**; the retire-queue was fine. The real cause of the BLACK PREVIEW was that `QmlVideoPreviewItem` (CPU) and `QmlVideoPreviewGlItem` are stacked in `VideoPreviewPanel.qml` and BOTH stay live, and both call `gst_app_sink_try_pull_sample()` on the SAME per-deck appsinks — a pull CONSUMES the sample, and those sinks are `max-buffers=1 drop=true`. The CPU item's 33ms timer was simply stealing most frames from the GL item. Worse, once the GL tail is in use the buffers are `memory:GLMemory`/RGBA and the CPU path was mapping them for CPU READ and reinterpreting as packed RGB888 (a forced GPU→CPU readback plus a format misread, every tick). **Fixed**: the two paths are now strictly mutually exclusive — `QmlVideoPreviewItem::poll()` returns early and `grabPreviewFrame()` hard-returns an empty QImage as soon as `isGlPreviewAvailable()` is true.
  2. **Handing GStreamer the wrapped Qt context.** `setSharedGlContext()` wrapped Qt Quick's CGL context via `gst_gl_context_new_wrapped()` and gave *that wrapper* to the pipelines, so `glupload` on GStreamer's streaming thread made **Qt's own context current while Qt's render thread was drawing with it**. One CGL context current on two threads is undefined behaviour that faults inside the GPU driver — which is exactly why both crashes produced NO macOS crash report (a driver fault never becomes a Mach exception). **Fixed**: the wrapped context is now only a share-group source; GStreamer gets its own context via `gst_gl_context_create(newCtx, wrappedQtCtx, &err)` and the pipelines get that. Textures stay in one share group so the path is still genuinely zero-copy.
  3. **Wrong GL API declared.** The wrap hardcoded `GST_GL_API_OPENGL3`, but Mixxx never sets a `QSurfaceFormat` version/profile (`WaveformWidgetFactory::getSurfaceFormat`), so macOS hands Qt a **legacy OpenGL 2.1 compatibility** context. `gst_gl_context_fill_info()` rejected the mismatch ("an opengl3 context created but the required ES2 compatibility was not found") and the whole path silently disabled itself — a "no crash" run that was really a silent fallback, not a success. **Fixed**: new `VideoEngineManager::GlApi` enum; the QML item reports the real flavour read off Qt's `QSurfaceFormat`.
  - **REMAINING BLOCKER (why it's disabled):** with the API finally correct, `gst_gl_context_fill_info()` stops bailing out early and starts issuing real GL queries against Qt's context — and crashes inside that call, on Qt's render thread, before the unbuffered stderr marker placed immediately after it can print. A separate self-inflicted crash was also fixed en route (`gst_gl_context_activate(ctx, FALSE)` lowers to `CGLSetCurrentContext(NULL)`, ripping Qt's context off the render thread mid-`updatePaintNode()`), but that was not the last one. **Conclusion: the whole GStreamer/Qt GL context handshake most likely cannot be done inline on Qt's render thread from `updatePaintNode()`** — a future attempt should do it on a dedicated GL thread (GStreamer's own context thread) with an explicit share/handoff, i.e. closer to how upstream `qmlglsink` structures it, rather than reaching into Qt's live render-thread context. **Diagnostic tip learned the hard way: `mixxx.log` loses its buffered tail on a hard crash — use unbuffered `fprintf(stderr)`+`fflush` and launch with stderr redirected to a file, otherwise every crash looks identical and silent.**

Clip looping (Stage 3x) never got a dedicated, isolated re-verification pass after the Stage 4 rewrite (it remains functionally solid through extensive real-world use).

## Packaging — a genuinely installable macOS .app (2026-08-02) — ✅ DONE

`cmake --install` had never produced a working bundle for this fork. Three
independent bugs, each hiding the next; all fixed (commit `8b1aa92b`).

1. **`BundleInstall.cmake.in` assigned every configured path unquoted**, so CMake split them on whitespace into list elements. A source tree containing spaces became `/Volumes/Deo;X9/Deo;Pro;DJ/...` (breaking the dependency search dirs and the entitlements path), and after the "Deo DJ" rename `BUNDLE_NAME` became the two-element list `Deo;DJ.app`, producing `fixup_bundle: not a valid bundle`. Upstream never hit this because `Mixxx.app` has no space. Quoting is still correct for the two genuine lists, since a CMake list configures to `"a;b;c"`.
2. **`BUNDLE_DIRS` only covered `CMAKE_PREFIX_PATH`** (the pinned vcpkg bundle). This fork also links whisper.cpp/ggml (FetchContent → binary dir) and ONNX Runtime, and `fixup_bundle` aborts with `otool -l failed` on any `@rpath` entry whose directory it was never told about. Added, guarded on the feature flags.
3. **Qt reserves `<bundle>/Contents/Resources/qml` as the bundle's QML import root**, and `MIXXX_INSTALL_DATADIR` pointed straight at `Contents/Resources` — so the entire skin landed inside that root. Type resolution then broke: `Settings/SoundHardware.qml` could no longer see `Skin.Slider`'s `slider` alias ("Cannot assign to non-existent property"), cascading up through `Settings.qml` → `TopBar` → `main.qml`, and the app exited during startup. **Bisected conclusively**: the identical binary with the identical files works when the resource path is *any* directory other than that reserved one (passing `--resource-path` explicitly was enough to mask it, which is what made this confusing). Resources now install to `Contents/Resources/mixxx`, with a matching branch in `computeResourcePathImpl()` that keeps the old location as a fallback. Upstream is unaffected because its bundles ship the legacy widget skin; the QML skin is experimental.

**Result**: `dist/Deo DJ.app`, 386MB, verified portable — copied to an unrelated directory with no source tree present and launched with no `--resource-path`, starting clean with all resources and vendored dylibs resolved from inside the bundle. Built with `AU_EFFECTS=ON` (see the correction under M8's infrastructure note).

**Signing — what is and isn't required** (all tested, not assumed):
- **No Apple certificate is needed to build or run.** Signed ad-hoc (`codesign --sign -`, no cert, no Apple ID, no Team ID) the app runs perfectly. Apple Silicon requires *some* signature — unsigned arm64 binaries won't launch — but ad-hoc satisfies that and is free.
- The only practical downside of ad-hoc is that its identity derives from the binary hash, so it changes on every rebuild and macOS resets TCC grants (camera/mic) each time. A stable cert avoids that re-prompting; that is the *only* reason to use one locally.
- **Hardened Runtime is not needed** for local use (it only matters for notarization) and is deliberately not used for `dist/`.
- **For distributing to other machines, the Development cert does NOT help**: `spctl` rejects both the ad-hoc and the Apple-Development-signed bundle once a quarantine flag is present. A clean install elsewhere needs a **Developer ID** cert plus notarization, i.e. the paid Apple Developer Program. Free workarounds: distribute off-web (USB/git — no quarantine flag, no prompt), have the user approve via System Settings → Privacy & Security → "Open Anyway", or `xattr -dr com.apple.quarantine <app>`.
- Current bundle: **arm64 only, macOS 11+**. Intel or universal would need a separate build.

Root cause: `AudioUnitBackend::loadAudioUnits()` queues manifest-loading blocks onto GCD's shared global queue and gives up waiting on them after a 6s timeout, but the destructor never waited for stragglers -- so a block from an *earlier, already-destroyed* `AudioUnitBackend` instance would eventually run, dereference its own now-freed `this`, and write into `m_manifestsById`/`m_mutex`, SIGSEGV inside a `QSharedPointer`'s atomic refcount. - ~~AudioUnitBackend thread-pool-exhaustion deadlock (surfaced by the crash fix above)~~ — **RESOLVED.** Naively fixing the crash (destructor blocks until all queued work finishes) turned the crash into a genuine hang: with dozens of AU plugins × 137 test-fixture-constructed `AudioUnitBackend` instances all queuing blocking work onto the *same shared* GCD global queue, the OS's shared worker-thread pool eventually fills entirely with threads parked on `dispatch_semaphore_wait`, leaving none free to ever do the work that would signal them -- a permanent deadlock, confirmed via `lldb` (all worker threads stuck at the same wait line). Fixed by switching `AudioUnitBackend` to own a private `NSOperationQueue` (`maxConcurrentOperationCount` = 8, replacing the old semaphore) instead of the shared global GCD queue -- exactly Apple's own documented use case for `NSOperationQueue` over raw `dispatch_async` (safe for long-blocking operations, gets its own dedicated thread pool, can't starve or be starved by anything else in the process). Destructor now does `cancelAllOperations` (drops anything not yet started -- the common case once the 6s timeout has already been hit) then `waitUntilAllOperationsAreFinished` (bounded to however long the handful of already-in-flight operations take, not the full backlog).
- ~~Incorrect `DEBUG_ASSERT` in `AudioUnitManager::waitForAudioUnit()`~~ — **RESOLVED.** Asserted `!success || m_isInstantiated`, but a real `AudioComponentInstantiate` error (a normal, already-explicitly-handled outcome one function up) legitimately produces `success=true` (the async block ran to completion) with `m_isInstantiated=false` -- the assertion was simply wrong, firing routinely (not a sign of memory corruption).   different (and correctly modest, ~0.1–0.2s) per-word refinements. User

  mechanism to detect or separate concurrent speech; every Whisper-based
  product has this same limitation. Considered and rejected: per-channel
  (L/R) transcription for panned-apart voices (narrow, unpredictable
  payoff — most mixes keep vocals centered) and routing through the
  existing AI Stem Separation feature first (Demucs separates vocals from
